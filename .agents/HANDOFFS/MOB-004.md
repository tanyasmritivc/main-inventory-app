## Executive assessment

The mobile app already contains most of the functional foundation needed for a first refurbishment without an architecture rewrite:

- Supabase authentication and session gating
- Streaming Ask FindEZ with conversation history, tool execution, attachments, and on-device speech input
- FIND multi-object photo extraction
- Barcode and FindEZ QR scanning
- Inventory, Spaces, sharing, teams, check-outs, low-stock tracking, documents, notes, spreadsheet import, BOM analysis, project kits, notifications, and profile management

The primary problem is product structure. Four visible shell tabs expose Inventory, Scan, Assist, and Profile while many important capabilities are nested, hidden, duplicated, or unreachable. The app opens on Inventory instead of the product's intelligence or physical-world action. ASK, Capture, and Find are implemented concepts, but the shell does not present them as the product model.

The critical trust gap is in capture persistence. FIND returns per-object identity, OCR, dimensions, confidence, reasoning, and a `needs_review` flag. The phone preserves those fields only through the pre-save review payload. The backend bulk-save path drops `scan_evidence`, stores no source frame, crop, mask, or bounding geometry, and creates no review record. The FIND job is deleted after mapping. A durable Review experience, visual provenance, source-frame item detail, and correction-driven training data therefore require backend work before mobile can present them honestly.

The recommended first implementation is a mobile-only information architecture and component pass that keeps all existing routes and behaviors, protects MOB-002, and does not pretend durable review exists. Durable capture and review should follow as a separate backend-first lane under FIND-001.

## Current architecture

### Application entry and state

- `mobile/lib/main.dart` initializes Flutter error hooks, cached plan state, local notifications, Supabase, app links, share-extension input, and the auth gate.
- Supabase Auth is used directly by Flutter. The FastAPI client attaches the current Supabase access token to requests in `mobile/lib/core/api_client.dart:13-53`.
- The app uses stateful widgets, static process-local caches, `SharedPreferences`, and direct API calls. There is no repository layer, state-management package, local database, or named-route router.
- `InventoryCache` is memory-only. Low-stock thresholds, onboarding state, and several preferences are device-local.
- The API base URL is supplied by `--dart-define`; the checked local mobile environment points at the current self-hosted FindEZ services. Secret values were not included in this handoff.

### Shell and navigation

`mobile/lib/features/shell/main_shell.dart` owns a four-page `PageView`:

1. Profile, internal page index 0
2. Assist, internal page index 1
3. Scan, internal page index 2
4. Inventory or Teams, internal page index 3

The visible bottom-bar order is Inventory, Scan, Assist, Profile. `initialPage` is 3, so Inventory is the signed-in landing screen. Inventory has a Spaces and Teams segmented header. Notifications, new chat, and shared-space joining are shell actions. Most secondary capabilities use imperative `MaterialPageRoute` pushes.

There is an implemented `HomePage`, but no live code constructs it. Documents are reachable from that dead page and from item detail, but the standalone Documents page is not reachable from the active shell. `SettingsPage`, `SharingPage`, the standalone `ActivityPage`, and the older `OnboardingFlow` are also not constructed by live navigation. These files are not safe to delete during refurbishment until their historical and platform uses are checked.

### Data and service boundaries

- Flutter calls FastAPI through `ApiClient` for inventory, spaces, sharing, teams, documents, project kits, activity, notifications, check-outs, usage, profiles, and scan extraction.
- Chat text is sent as server-sent events to `POST /ai_command?stream=true`.
- Chat attachments are streamed from `POST /ai_upload`.
- Photo capture calls `POST /inventory/extract_from_image`, which invokes the external FIND service from the backend.
- Bulk save calls `POST /inventory/bulk_create`.
- Google, Apple, email/password, email verification, and password recovery are implemented through Supabase.

## Detailed audit

### 1. App architecture and navigation

Classification: MODIFY

What works:

- The shell preserves each primary page in a `PageView`, so tab state survives switches.
- Push notifications, shared-space joining, team navigation, and Ask navigation hints are integrated at shell level.
- Major functional surfaces already exist and can be regrouped without removing them.

Problems:

- The current four-tab model does not express ASK, CAPTURE, FIND, MEMORY, PROFILE.
- Inventory is both a Space browser and a search result screen, and it is the default landing page.
- Teams share the Inventory slot through a segmented control, while Documents, check-outs, project kits, and import are buried elsewhere.
- There is no typed route graph or centralized destination registry. Navigation logic is spread across large widgets.
- `main_shell.dart`, `inventory_page.dart`, `chat_page.dart`, `scan_page.dart`, and `shared_inventory_page.dart` are very large and mix networking, state, navigation, and presentation.

Direction:

- Build a five-destination shell: Ask, Capture, Find, Memory, Profile.
- Make Ask the signed-in entry point unless later product testing demonstrates that Capture converts better.
- Preserve all existing detail routes and actions, but surface them under Memory or Profile.
- Introduce a small destination model and focused page controllers during implementation. Do not add a large framework merely for navigation.

### 3. Capture and Scan experience

Classification: MODIFY now, then REBUILD the result/review stage after FIND-001

Already implemented:

- Camera and photo-library input.
- Multi-object FIND extraction.
- Barcode camera scanning and barcode lookup.
- FindEZ item QR lookup and Space QR flow.
- Image resizing and JPEG compression on both the page and API client path.
- Staged progress text, long-wait hint, timeout dialog, retry, plan-limit handling, and partial-save handling.
- Editable confirmation sheet for FIND results.
- Destination Space selection and Space creation.
- Spreadsheet import, BOM readiness, and project kits from Space detail.

Evidence:

- Photo selection and FIND request: `mobile/lib/features/scan/scan_page.dart:1057-1248`.
- Barcode/QR handling: `mobile/lib/features/scan/scan_page.dart:411-628`.
- Save and partial-failure logic: `mobile/lib/features/scan/scan_page.dart:1534-1778`.
- Visible capture toggle: `mobile/lib/features/scan/scan_page.dart:1900-2050`.

Problems:

- The live Scan screen presents only a two-way Barcode/FIND Photo toggle. Spreadsheet, BOM, and project-kit entry points are nested under individual Space views, so Capture does not communicate the full intake surface.
- The screen starts with no selected Space. The user can scan first, but save later stops and opens the Space picker. Destination should be chosen or clearly deferred before the expensive action.
- The UI displays generated stage text while the backend exposes no real per-stage job progress to the client.
- The phone compresses the image once and `ApiClient` can compress it again to 1280px at quality 80. This may remove label detail before FIND OCR or measurement.
- A timeout causes a new retry. There is no resumable capture ID or job lookup.
- Results are rows, without source-frame overlays or per-object crops because the response contract does not contain them.
- `needs_review` causes confirmation but has no durable queue. Save accepts all valid names, including `Unidentified item`, unless the user removes or edits them.
- Duplicate-name aggregation can merge distinct detected objects and the client contains explicit handling for silent drops.

Direction now:

- Make Capture a first-class destination with Photo first, Barcode second, and explicit Import and BOM entry points.
- Put the Space destination near the capture action and remember the last used Space locally.
- Explain what will happen before upload and show truthful phase language.
- Keep existing confirmation and per-row correction until durable review exists.
- Add client-side guards against obviously unresolved identities before save, but do not invent a persistent review queue.

Direction after FIND-001:

- Show the source frame with object geometry, per-object crops, and a list.
- Allow save-resolved and send-unresolved-to-review only when unresolved objects are durably stored.
- Persist corrections, missing-object boxes, and false-positive deletions.

### 4. FIND integration

Classification: KEEP the backend boundary and evidence mapping, MODIFY reliability, REBUILD persistence

Already implemented:

- The backend creates a FIND job, runs segmentation with Qwen3-VL proposals, identification, and measurement, polls to completion, maps results, and deletes the FIND job.
- Mapping exposes identity, category, vendor, SKU, barcode, confidence, notes, OCR, dimensions, measurement method, detection confidence, and `needs_review`.
- Flutter parses and displays scan evidence in the pre-save confirmation flow.

Evidence:

- FIND orchestration: `backend/app/services/find_pipeline.py:243-399`.
- Evidence mapping: `backend/app/services/find_pipeline.py:117-168`.
- Mobile evidence model: `mobile/lib/core/api_client.dart:1628-1765`.
- Multi-object route: `backend/app/api/routes/items.py:471-561`.

What is not implemented:

- The multi-object route does not call the image storage service.
- The mapped response has no crop URL, source image URL, mask, polygon, or bounding box.
- `bulk_create_items` does not include `scan_evidence` in the database payload.

- The FIND job and its artifacts are deleted in `finally`.

Implication:

The app may use evidence to help the user review immediately, but it cannot claim that an inventory record remembers the photo, object crop, geometry, naming method, or original evidence after save.

### 10. API and backend integration

Classification: KEEP contract coverage, MODIFY client structure

### 11. AI streaming

Classification: KEEP, MODIFY implementation

- Text and file streaming are already implemented over SSE.
- The UI incrementally presents content and preserves conversations.
- Navigation hints can open relevant product destinations.

Risks:

- Two stream parsers have different assumptions. `ApiClient` accepts lines beginning with `data:`, while Chat text requires `data: `.
- Chat's parser expects a `content` field in one path, while `AiStreamEvent` models `delta` in another.
- JSON parsing failures are swallowed, which can end with a blank or generic answer without telemetry.
- Presentation timers and fake typing add complexity around real stream timing.

Direction:

- Consolidate on one event schema and parser with tests for chunk boundaries, status, delta/content, completion, tool events, malformed events, disconnect, timeout, and resume behavior.

### 15. Accessibility

Classification: REBUILD baseline

Findings:

- Only a small number of explicit tooltips exist. No explicit `Semantics` widgets or `semanticLabel` properties were found in Flutter source.
- Many actions use bare `GestureDetector` and styled `Container`, which lack button semantics, keyboard behavior, focus states, and guaranteed touch targets.
- `main.dart` explicitly sets `MediaQuery.boldText` to false, overriding an operating-system accessibility preference.
- Some text uses very low white alpha on black and very small 10 to 12px labels.
- Custom icons, QR cards, image thumbnails, and progress indicators often lack accessible descriptions.
- Some custom motion honors reduced motion, but most repeated motion does not.

Required first-pass acceptance criteria:

- Do not override bold text or text scaling.
- Use semantic buttons and labels for every action.
- Verify 44 by 44 point touch targets.
- Provide image and status descriptions.
- Support Dynamic Type without clipped navigation or actions.
- Verify VoiceOver order and escape behavior for sheets.
- Honor Reduce Motion for all repeating and decorative animation.
- Test contrast for text, controls, focus, success, warning, and danger.

### 16. Performance

Classification: MODIFY

Strengths:

- Scrolling item results generally use `ListView.builder`, `ListView.separated`, or `GridView.builder`.
- Inventory loads related top-level datasets in parallel.
- Image input is compressed before upload.
- Some data is cached between tabs.

Risks:

- Inventory and several helper flows fetch every item using an empty search query.
- There is no server pagination contract in the mobile client.
- Images use `Image.network` without an explicit disk-cache package or consistent sizing.
- Document note search downloads notes sequentially.
- Profile and documents fetch signed URLs or images within screen load paths.
- Several screens poll on timers.
- Large monolithic stateful widgets cause broad rebuilds and make profiling difficult.
- Photo processing uses the Dart image package in the UI isolate. Large images can stall frames before upload.
- Scan can compress twice, potentially adding CPU time while reducing recognition quality.

Priority:

1. Instrument capture timings and remove duplicate compression.
2. Add backend pagination and query filters before large inventory UI expansion.
3. Split state and rebuild boundaries during screen refurbishment.
4. Add measured image caching and thumbnail sizing after durable crop URLs exist.

## Product blueprint

### ASK

Purpose: Ask the physical memory a question and act on the answer.

First refurbishment, current backend:

- Make ASK a primary destination and signed-in entry.
- Preserve streaming, conversation history, attachments, microphone, tool actions, and navigation hints.
- Present suggested inventory questions only when the conversation is empty.
- Make citations to Spaces, items, documents, project kits, and teams tappable through existing navigation hints where supported.
- Consolidate the SSE parser and add transport tests.

Requires backend work:

- Referenced source frames or object crops in answers require FIND-001 persistence and tool/context support.
- Cross-device voice transcription through gateway Whisper requires a backend proxy endpoint. It is not needed for the first refurbishment because on-device speech already works.

Future only:

- Proactive ambient memory or continuous capture. No current sensor, permission, or backend architecture supports it.

### CAPTURE

Purpose: Turn a physical observation into structured memory.

First refurbishment, current backend:

- Make Capture a primary destination.

## Smallest backend/API changes for the first refurbishment

The shell, Ask, Capture entry points, Find search, Memory organization, Profile organization, theme consolidation, loading states, and accessibility pass can begin with zero backend changes.

The smallest backend change set for the first trustworthy visual-memory release is FIND-001. The exact names below are proposed new contracts, not current fields:

1. Persist one capture record with owner, destination Space, source image storage path, image dimensions, lifecycle status, creation time, and deletion/retention time.
2. Persist one object record per FIND result with capture reference, stable object ID, normalized geometry or mask reference, optional crop path, raw identity result, current proposed identity, confidence, OCR, measurement evidence, review state, and optional created inventory item reference.
3. Add correction events with three explicit event kinds: identity correction, user-added missing object geometry, and deleted false positive. Preserve before and after values and actor/time.
4. Add authenticated endpoints to create or finalize a capture, list unresolved objects, retrieve one review object with signed media URLs, and submit a review decision.
5. Make bulk creation or finalize-capture transactional so resolved items and review state cannot disagree.
6. Publish and enforce a source-image, crop, mask, and correction retention policy with a defined deletion timeframe and user deletion behavior.
7. Keep FIND service credentials and storage signing server-side.

Do not add a split `Save resolved` action until steps 1 through 5 exist. Client-memory-only unresolved objects would be lost.
