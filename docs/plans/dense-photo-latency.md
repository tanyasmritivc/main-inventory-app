# Crowded photo latency

Crowded photos previously repeated identification after every close-up had already located the objects. The original sample took 218.88 seconds; simply enlarging crop batches hit the 240-second deadline in a new benchmark, so that approach was rejected.

Large-image overviews now perform a quick survey, leaving tiny-part enumeration to the overlapping high-resolution views. Six bounded workers cover all portrait sections in one wave. Close-ups locate and identify each object together, returning the existing identity/count/OCR evidence contract inside its detection. Valid whole-object close-up observations are preferred over coarser overview duplicates. Only crops without valid details need a separate identification call; that fallback retains the original two-crop resolution and four-worker behavior.

Invalid details never discard a valid detection: the crop falls back to identification, and any remaining failure stays explicitly unknown/partial. Stable output/region IDs survive noncontiguous fallback batches. Group/occlusion counts remain unknown; printed labels are required for dimensions and part numbers. No object ceiling, new model/provider, inventory write, schema change, save/destination change or client UI change is included. Main Chat is untouched. Existing web/mobile clients use this shared backend without a binary update.

Validation: 1,569 backend tests passed. Coverage includes bounded portrait concurrency, preserved identities across deduplication, malformed-detail fallback, noncontiguous crop/index association, no repeated calls for already-read items, and failed fallback preserving neighboring results. Live no-save benchmark and production-candidate checks are being completed. Deploy only after measured improvement and all five exact-commit CI gates; preserve every other production Python file.
