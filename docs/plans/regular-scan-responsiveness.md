# Regular scan responsiveness

Deployed shared backend runtime `35129bf570f90ca56e65e0eb0f5a727402c76417` after all five CI jobs passed in run `42506078089`. One runtime file changed; 147 other Python files were preserved. Health, database and anonymous authorization checks passed. No client binary or database change.

Small scans now identify each detected crop individually in the existing four-worker pool. Up to four detected regions use this scheduling path; larger scans retain the existing two-crop batches. This confines individual reads to one worker wave. This is never an item limit. Grounding, crowded-photo close-ups, all accepted objects, source-coordinate crops, unknown-count rules, saving, destinations and client/main-chat behavior are unchanged. Individual crops retain up to 1280-pixel detail instead of fitting into a roughly 620-pixel contact-sheet tile. Failures retain the detected crop as an explicit unknown, as before.

The work is intentionally limited to the shared extractor. Inspection confirmed the deployed web/mobile preview path emits a durable capture and a terminal done event without waiting for a chat response. A disposable-account candidate HTTP check received exactly one done event, nonempty editable items with image URLs/evidence, and keepalives no more than ten seconds apart. It created no inventory and removed the account and its temporary images. The user's indefinitely loading case was not reproduced by that check; physical-device acceptance remains unverified.

Validation: 62 focused tests, including one/four/eight/nine-object scheduling, full crop pixels, four-worker concurrency, stable mapping, retained large-scene batching, partial failures, save/crop/evidence contracts; full Python suite 1,568 passed. The isolated production candidate also passed all 62 focused tests. No database or native changes.

A normal charger-photo inference-only check took 29.55 seconds before and 21.12 seconds with the candidate. Both identified four items; model detection varied (five versus four regions). This is a single-run comparison, not a guaranteed speed/accuracy improvement. The complete candidate HTTP path took 52.6 seconds, returned four identified items and no unknowns. The current live HTTP path took 44.3 seconds for the same photo (four identified and one unknown); this mixed result does not establish a total latency improvement. With four identical accepted crops held constant, successful paired reading took 18.15s; single-crop reading took 13.56s and 23.32s. All three runs identified all four items. Another paired run took 45.41s and hit an upstream HTTP 500, retaining two unreadable regions as unknown. These measurements are mixed; they do not prove a general end-to-end speedup. Individual reads provide fuller crop resolution and isolate each item failure, with no additional worker wave for eligible small scans. Shorter JSON prompts and streaming transport probes were also investigated without establishing an end-to-end improvement and are excluded. No claim is made that every scan is faster or that an upstream model timeout has been eliminated.

The exact released source passed a full candidate HTTP scan in 32.0 seconds (five regions, four identified, one unknown), with its source hash recorded in the receipt. This five-region case intentionally uses the unchanged paired path. The durable draft and terminal done event arrived, the largest response-line gap was ten seconds, no stock was saved, and all disposable QA data was removed. Production HTTPS acceptance completed in 46.6s with six detected regions, four identified and two explicit unknowns. It returned a durable draft, photos/evidence and terminal done event; invalid authentication was denied. The disposable account and seven test images were removed, and no inventory was saved. This six-region acceptance case uses the unchanged paired path, so its timing is not evidence of a scheduling speedup. See regular-scan-release.json.

The reported stuck-loading behavior was not reproduced. Upstream model latency/errors remain possible; this release is a bounded small-scan scheduling improvement, not a promise of instant results or elimination of every hang. The separate crowded-photo investigation remains rejected and was not deployed.
