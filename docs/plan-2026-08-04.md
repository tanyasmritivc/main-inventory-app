# Azure vs. season — decision and 4-week plan (2026-08-04)

## Decision (owner, 2026-08-04)

**Supabase stays. Everything else moves to Azure.** No Render, no Vercel.

- **Stays on Supabase:** Postgres, Auth, Storage.
- **Moves to Azure:** backend host (Render → App Service / Container Apps), web host
  (Vercel → Azure), and OpenAI → Azure OpenAI.

Driver is **consolidation, not compliance** — an admin account exists because ftctools.com is
already on Azure. No external deadline attached to the migration itself.

**Zero real users today.** Season (FLL/FTC/FRC/VEX) starts in ~4 weeks.

## Why this split is the right one

The pieces that move are the pieces that don't touch `user_id`. Hosting and the model provider are
config-level changes with a blast radius you can see. Postgres, Auth and Storage are the ones where
a mistake is unrecoverable, and they are exactly the ones staying put.

The migration deadline is soft. The season deadline is not — teams organise in the first weeks of
the season and are hard to reach after. That asymmetry decides everything below.

**But the zero-users argument cuts the other way and deserves a straight answer.** Auth is the one
piece that gets more expensive with users, `user_id` is a FK on effectively every row, and today
there is nothing to migrate. The next window this clean is roughly May–August 2027, because FTC
runs Sept–Feb and FRC runs Jan–April with no real gap between them.

That argument is real. It loses anyway, for one reason: a botched auth cutover at kickoff is
unrecoverable *this season*, while staying on Supabase Auth costs nothing a user can see. Auth
migration is 2–3 weeks of work with no test coverage and one physical test device. Spending that
now means arriving at kickoff with no bins, no offline, and a login system nobody has stress-tested.

### The move that makes deferring auth cheap

Do this small thing now instead, while there are no users:

**Stop assuming `user_id == auth.uid()`.** Introduce an internal `users` table keyed by your own
UUID, with the identity provider's subject as a mapped column. Every other table's `user_id` FK
points at *your* table, not `auth.users`. Then the eventual auth migration re-maps one column
instead of re-keying the entire database.

At zero rows this is a one-hour migration. At ten pilot teams it is a weekend. It converts the
expensive future migration into a cheap one and is worth doing regardless of what else happens.

Note this also removes two existing couplings to Supabase Auth: the
`conversations.user_id → auth.users(id) ON DELETE CASCADE` FK in migration `009`, and the
`supabase/functions/delete-user` edge function.

### The Azure moves, in order of risk

**1. Backend: Render → Azure App Service or Container Apps.** Do this first; it is the one with a
user-visible payoff. Render's free tier spins down after 15 minutes with a 50s+ cold start, while
mobile timeouts are 20s (`_loadItems`) and 30s (Dio) — so a team opening the app for the first time
at kickoff currently gets a broken app. Moving to an always-on Azure plan fixes that outright.

Watch: the SSE byte padding at `routes/ai.py:334` exists specifically to defeat Render's proxy
buffering. It may be unnecessary on Azure. Re-test streaming before deleting it, don't assume
either way. Keep `X-Accel-Buffering: no`.

**2. Web: Vercel → Azure.** Low stakes — the pit uses the mobile app, and roughly zero frontend
work is planned this cycle. Next.js 16 needs server rendering, so prefer **Container Apps or App
Service** over Static Web Apps unless the site turns out to be fully static. Move it whenever;
it blocks nothing.

**3. OpenAI → Azure OpenAI.** Recommended, with one hard prerequisite.

Right for this project because the compliance story is the product's, not just the infrastructure's:
SOC 2 Type II, ISO 27001, regional data residency and private networking. You have committed to
conservative handling of minors' data and that promise will be read by mentors and educators.
"Runs in our Azure tenant" is a materially better answer than "we call an API." Azure's day-one
model lag — the usual reason to stay direct — does not apply to you, because `gpt-4o` and
`gpt-4o-mini` have been on Azure for a long time.

**Prerequisite, and it is the thing that would silently kill chat at kickoff:** new Azure
subscriptions frequently start at **0 TPM quota** for a given model, region and deployment type
until an increase is approved. Request quota for `gpt-4o` and `gpt-4o-mini` in your region on day
one, before writing a line of code, and confirm the approved TPM is non-zero. Everything else here
is reversible; arriving at kickoff with 0 TPM is not.

Code impact is contained but not zero: swap to the `AzureOpenAI` client (endpoint + `api_version` +
deployment names instead of model names), and note that `gpt-4o-mini` is pinned at **four** sites —
`openai_service.py:347, 515, 605` and `ai_memory.py:58` — plus `settings.openai_model`. Those pins
exist because reasoning models 400 on system prompts; preserve the pinning, just point it at a
deployment.

Postgres, Auth and Storage stay on Supabase indefinitely. If they ever move, the `users` table
above is what makes it cheap.

## Kill the payment problem instead of solving it

There is no StoreKit path, so Stripe Checkout inside the iOS app is an App Store rejection.
**Make the pilot free.** Ten hand-set-up teams, free for the season. That defers the entire
Stripe/IAP question past the season, and it aligns with the "free for students" commitment that
was already non-negotiable. It also removes the need to reconcile the two mounted Stripe routers
under time pressure — just unmount `billing.py`.

## Two weeks (hard plan), one month (ceiling)

Everything below the two-week line is month-mode only. If the month doesn't materialise, the
pilot still works without it.

### Day 0 — today, ~2 hours

1. **[Azure portal] Request quota** for `gpt-4o` and `gpt-4o-mini` in your region. Default can be
   0 TPM and approval is not instant. Nothing depends on it today; it just needs to start.
2. **[local] `rm .git/index.lock`**, then commit and push the three doc changes.
3. **[Supabase SQL editor] Baseline the schema.** Paste the output into
   `backend/supabase/migrations/010_baseline.sql` and commit. Eleven tables the code depends on
   have no `CREATE` anywhere in the repo. Nothing else here is safe until this exists.

   ```sql
   SELECT table_name, column_name, data_type, is_nullable, column_default
   FROM information_schema.columns
   WHERE table_schema = 'public' ORDER BY table_name, ordinal_position;

   SELECT schemaname, tablename, policyname, cmd, qual, with_check
   FROM pg_policies WHERE schemaname = 'public' ORDER BY tablename, policyname;

   SELECT conrelid::regclass AS table_name, conname, pg_get_constraintdef(oid)
   FROM pg_constraint WHERE connamespace = 'public'::regnamespace ORDER BY 1;
   ```

4. **[Supabase SQL editor] Run the orphan query** from `docs/session-handoff-2026-07-30.md` §5.
   The answer decides whether step 8 is a real bug fix or already closed. Also settle the
   `items.created_at` type question while you are in there.

### Days 1–3 — infrastructure and unblocking

5. **[Azure] Backend → App Service or Container Apps**, always-on plan. Repoint `api.findez.ai`.

8. **[Windsurf · BACKEND ONLY] Close the rename/orphan bug** if step 4 returned rows.

### Days 4–8 — bins, the actual blocker

9. **[Decision] Bins are a table, not a text column.**

   ```
   bins(id uuid pk, user_id uuid, space_id uuid fk, name text, created_at timestamptz)
   items.bin_id       uuid null fk → bins(id) on delete set null
   items.home_bin_id  uuid null fk → bins(id) on delete set null
   ```

   The QR encodes `findez://bin/<uuid>`, **not** the name. If bins are free text keyed by name,
   renaming a bin silently orphans every printed label — which is precisely the space-rename bug
   you just spent a week on. Pay the small cost now.

10. **[Windsurf · BACKEND ONLY] One migration**, `011_bins.sql`: the table plus both item columns.
    Do not split this across two migrations. Then `services/bins_repo.py` and
    `GET|POST /bins`, `PATCH|DELETE /bins/{bin_id}`, `GET /bins/{bin_id}/items`. Return `bin` in
    `/search_items` and every item payload.
11. **[Windsurf · BACKEND ONLY] Ground the AI on bins** — add bin to item context in
    `openai_service.py` / `ai_agent.py`, so "where are the M3×10s" answers with the bin rather than
    the room the student is already standing in.
12. **[Windsurf · MOBILE ONLY] Surface bin** in search results, item detail sheet, item editor.

### Days 9–12 — labels and mentor setup

13. **[Windsurf · MOBILE ONLY] Real bin labels.** `bin_label_sheet.dart` currently prints *space*
    labels (`findez://space/<name>`). Point it at bins, and make scanning a bin QR open that bin's
    contents with an "add item here" action.
14. **[Windsurf · MOBILE ONLY] Mentor setup flow**: create team → import BOM → print labels →
    share code, completable in 30 minutes with no support.
15. **[local] Fix the malformed final line in `.gitignore`.**

### Days 13–14 — buffer

No new work. There is no CI and one physical test device; regressions only appear on device.
Run `test-data/release-checklist.md` §2, §5, §6, §7 — including §6 from a **second account**.
